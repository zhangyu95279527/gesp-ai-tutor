# 确认与L1原子受理切片

日期：2026-11-13；TASK-0024。

- 现状：原ConfirmationService提交扣次后，调用方需另调attach_l1；两个事务之间退出会留下已扣次但无阶梯操作的记录。TASK-0023仅处理已存在的阶梯。
- 新LadderAdmissionService复用确认校验/额度/冻结逻辑，覆写持久化钩子，在同一连接/事务写入L1操作和steps，并占用原确认执行权。生产默认generation_ready=False；不提供未经安全/预算装配的成功HTTP入口。
- 同键重放仍返回原操作号；不重新计次。事务任何位置失败，PG业务与额度一并回滚；Redis后续按PG账本恢复。
- 旧ConfirmationService保留给尚未迁移的调用与原测试，不隐式更改旧认领器行为；新生成装配必须选新原子入口，避免组合旧confirm+attach。
- 孤立恢复只处理l1_pending会话、没有同ID阶梯操作、受理时间已过120秒、状态admitted/running/interrupted的确认。会话→确认锁后重查，无其他活动阶梯时写入同ID的interrupted操作与原受理时间的steps，不调用模型或额度服务。
- 恢复的created_at/deadline_at取原确认时间，不重赠执行期限；原确认保持interrupted。后续显式retry_l1按新请求计1次。
- 孤立恢复与既有过期扫描共用总批次上限50。并发扫描、正常attach与新确认以会话锁串行，既有阶梯不覆盖；确认已完成/未到期/超限拒绝不误恢复。
- 本轮无迁移与UI变化。真实模型、安全、资源预算、供应商取消、运行中SSE和PC真实端到端仍由TASK-0021承担。
- 用户要求每轮保持Git同步：完成验证后提交/推送，组件先于交付仓；固定chore-mac-mini-handoff换机分支仅快进到当前已保存进度。远端有新提交或分叉先停止推送并处理，不强推。工作区/环境/未完成项写入最新检查点。

停止条件：API规范/类型/全回归、同步脚本故障保护测试、三仓任务/换机远端SHA核验及最新检查点齐备。没有新的G4或发布声明。
